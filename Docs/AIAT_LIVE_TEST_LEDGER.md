## How to use this ledger

This file is both the test plan and the durable result record. A feature is not considered verified because an old plan says it passed, because a route exists, or because a unit test is green. Update the corresponding row after every test.

Status values:

- `NOT_RUN`: no current-run evidence.
- `RUNNING`: a live test is in progress.
- `PASS`: the stated proof was observed in the current run.
- `FAIL`: behavior contradicted the expected result.
- `BLOCKED`: the test could not run; the exact external or environmental blocker is recorded.
- `PARTIAL`: only part of the stated proof was demonstrated.
- `DEFERRED`: intentionally not implemented; this is acceptable only when current plans explicitly defer it.
- `N/A`: superseded or rejected architecture; the reason must be recorded.

Result quality:

- `STATIC`: code/config/doc inspection only.
- `CONTRACT`: automated schema, unit, or policy test.
- `INTEGRATION`: multiple real services or dependencies exercised.
- `LIVE_API`: request made against the running stack.
- `LIVE_UI`: operator workflow completed in the real dashboard.
- `RECOVERY`: restart, crash, timeout, replay, or resume behavior actually exercised.
- `EXTERNAL`: real optional provider/runtime/tool exercised.
- `SECURITY`: security-boundary or least-privilege proof.

Every update must preserve these fields: status, proof level, date/run ID, exact evidence, defect/fix, and enhancement/next action. Never replace a current failure with an old passing count. Append detailed commands and artifacts to the run log and place a short pointer in the matrix.
