1. The platform should provide a web-based orchestration flow builder and visualization layer. I want to be able to create, edit, and visualize new orchestration flows through the UI, and have those flows available for use by the CEO agent or manually selected by me for a given project, task or departement. A flow should represent a configurable execution graph that defines stages, transitions, responsible agents or teams, branching conditions, approval gates, retries, escalations, and completion rules. These flows should not be hardcoded into agent logic; instead, they should exist as managed workflow definitions stored by the platform and interpreted by the orchestration/controller layer at runtime. The UI should support both visual design and operational visibility: I should be able to model a new flow, inspect which flow a project is currently following, see the current node/state, review past transitions, and override or switch flows when appropriate. The CEO agent should be able to invoke these flow definitions as part of project coordination, but the human operator must also retain the ability to assign or customize flows directly from the interface. This makes orchestration adaptable to different project types and allows the system to evolve toward a configurable workflow platform rather than a fixed single-process pipeline.
2. Workers should be modeled as configuration-driven integration units. Instead of treating workers as directly embedded code modules, the system should treat them as YAML-defined contracts that describe how a capability is integrated into the MAS. Each worker configuration should specify the worker identity, source repository, version pinning, integration mode, adapter/driver entrypoint, runtime requirements, allowed tools, schemas, limits, and update policy. When hiring a new agent, we provide the original GitHub repository URL and ingest it into an upstream mirror. The platform then evaluates the repository for architectural fit, maintenance quality, licensing, security, and compatibility with our orchestration model. If approved, the repo is integrated through a thin compatibility layer that adapts it to our internal protocols rather than by deeply rewriting the upstream codebase. Any custom behavior required by our architecture should be implemented in wrappers, adapters, and isolated patches, so the original source remains as untouched as possible. This approach lets us maintain a private managed fork only as an integration shell, while upstream evolution remains trackable and mergeable. New upstream updates can then be re-pulled, validated through compatibility tests, and merged with minimal friction. This design also allows workers to be activated, deactivated, upgraded, replaced, or reclassified as tools/services without destabilizing the rest of the system.
2.1. The platform should provide a centralized tool integration layer for all workers. Shared capabilities such as browser automation, web access, search, document handling, storage access, and other operational tools should be implemented as centrally managed services rather than as worker-specific dependencies. Workers should consume these tools through a common interface governed by the platform, with consistent authentication, authorization, rate limiting, caching, auditing, and error handling. This design ensures that external agents integrated into the system do not bypass architectural controls by bringing their own unmanaged tooling stack. It also makes tool behavior predictable and reusable across all teams, while allowing the platform to enforce policy, observe usage, and evolve tool implementations independently of worker logic. In practice, this means capabilities like browser access should be offered once as a centralized service and then made available selectively to workers according to role, permissions, and workflow needs.

The AIAT database architecture should be a **Postgres-first, project-scoped knowledge and workflow model** where Postgres is the canonical source of truth for all structured state, MinIO stores the heavy file bodies, and retrieval sits on top rather than replacing the schema: keep core relational tables such as `projects`, `documents`, `reviews`, `approval_gates`, `sprints`, `issues`, `kpi_metrics`, `project_state_history`, `agent_profiles`, `dead_letters`, `system_config`, and `agent_checkpoints` to represent workflow, versioned documents, approvals, execution history, agent learning, failures, and shutdown-safe resume state; store uploaded files, generated artifacts, diagrams, retrospectives, and large document bodies in MinIO with stable blob references; then add a dedicated **project context layer** in Postgres—such as `project_context_items`, `project_context_chunks`, tags, and relationship/link tables—so every project has its own persistent knowledge space visible in the UI and queryable by agents; use normal SQL and typed APIs for exact records and workflow truth, and use **hybrid retrieval** only for unstructured context by filtering first by `project_id`, then combining metadata search, keyword search, and optional pgvector semantic search over chunked text, so agents can fetch the most relevant passages from project files without turning the whole database into “just RAG”; in practice this gives you a clean separation of concerns: **Postgres for structure and authority, MinIO for content storage, pgvector/hybrid retrieval for semantic access, and the orchestrator/controller as the sole writer of lifecycle state**, which matches the existing MAS plans and is the safest, most extensible architecture for AIAT.   
4. The system should expose a unified operational control layer through dedicated scripts or command wrappers. This control layer should centralize the operational actions needed to administer the platform, including bootstrapping, shutdown, restart, service inspection, log access, diagnostics, cleanup, and routine administrative workflows. The goal is to make system control predictable, repeatable, and automation-friendly, whether the stack is managed directly through Docker Compose or integrated with a service manager such as systemd. Compose supports the core lifecycle operations needed for this model, while systemd is explicitly designed to introspect and control the state of services and implements restart behavior as stop followed by start.
5. I want a web UI that visualizes the full team hierarchy, communication permissions, and possible orchestration flows of the system. The interface should let me inspect how teams and agents are organized, which communication paths are allowed, and what orchestration routes can be used for projects or tasks. This should be interactive and operational, not just a static diagram, so I can explore structure, trace workflow paths, and better understand how the system behaves. React Flow and Cytoscape.js are both well suited to this kind of interactive graph-based interface, while Mermaid is useful for simpler architecture and flow visualizations.
6. The platform should provide a centralized credentials manager that is the only component allowed to access real secrets such as environment values, API keys, tokens, and other protected credentials. The rest of the system should work only with named secret references or placeholder values, for example LLM_API: <LLM_API>, so agents and LLMs can understand which credential is required without seeing the real secret itself. When code execution, tool usage, or configuration generation requires a credential, the request should be sent to the credentials manager using the key name and execution context, and a controlled adapter or middleware should resolve and inject the real value only inside the approved execution path. The credentials manager should also support per-secret configuration, usage rules, and policy-based decisions so the system can determine whether a secret should be made available for a specific use case or refuse access when the request is not justified. This would allow the platform to preserve correct configuration semantics for agents while enforcing a strict boundary that prevents credentials from leaking outside the credentials manager.
7. The platform should support multiple LLM APIs through an enhanced centralized LLM gateway that serves as the single model access layer for the entire system. This gateway should unify provider access, expose a stable common interface, and make intelligent routing decisions based on factors such as task type, quality requirements, cost limits, latency targets, context size, tool-calling support, structured-output support, and fallback availability. In addition to serving native internal workers, the gateway should also expose an API or compatibility adapter that allows GitHub-cloned agents to use the same centralized LLM layer instead of relying on their own direct provider integrations. This would ensure that all model usage passes through one controlled boundary where routing, observability, budgets, security, and provider governance can be enforced consistently across the platform.
8. The platform should enhance the CEO into a secure executive copilot role that serves as the primary middleware and direct contact between the human operator and the MAS. The CEO should be responsible for reliably carrying instructions, context, alerts, escalations, and summaries between me and the rest of the system, and it should be able to act on my behalf when I explicitly authorize it to do so. It should have the broadest orchestration visibility and coordination capabilities in the platform, and it may internally rely on one or more powerful underlying agent candidates, but it must remain the single top-level executive role inside the MAS. To keep this design powerful without making it dangerously overprivileged, the CEO’s authority should be split into two clearly separated layers. The first layer is executive authority, which covers orchestration, project supervision, communication with all teams, workflow steering, alerting, status aggregation, and acting as my operational copilot inside the MAS. The second layer is privileged operations, which covers highly sensitive actions such as access to system control scripts, team shutdown and restart commands, container control, and other infrastructure-level operations. These privileged operations should not be treated as normal CEO permissions. They should be gated through stronger controls such as explicit policy checks, full audit logging, restricted execution paths, and optional step-up approval from me depending on the action. Because the CEO is the most sensitive role in the system, it must also be the most protected and monitored. It should be continuously supervised by dedicated security controls, operate under strict policy enforcement, and remain isolated by stronger safeguards than any other team or agent. The CEO should also have access to the UI through its own dedicated user identity, separate from mine, and I should be able to lock or restrict specific sections of the interface so that the CEO can access only the parts that I explicitly allow. This way, the CEO becomes a highly capable and autonomous copilot for the MAS, while its most dangerous powers remain controlled, auditable, and safely separated from its normal executive role.
